# 상품 사양 비교

출처가 첨부된 상품 JSON을 받아 조건에 맞는 상품을 고르고 사양 표 데이터를 반환합니다. 상품이나 시계 모델을 하드코딩하지 않습니다. 웹 검색, 페이지 수집, 출처 진위/최신성 검증, 추천 점수 생성은 하지 않습니다. 호출자가 확인한 사양을 공급해야 합니다.

`run({"payload": {...}})` 또는 stdin JSON / stdout JSON을 사용합니다. Agent 프롬프트에서는 `product-comparison {JSON payload}`로 결정론적으로 호출합니다. 일반 자연어에서 인터넷 상품을 찾는 전체 과정은 별도의 검색 계층이 필요합니다.

- `fields`: 필드명별 `type` (`number`, `string`, `boolean`)과 `unit`. 숫자는 명시적 단위가 필요하고 나머지 단위는 null입니다. 단위 없는 숫자는 `count`, 비율은 `ratio`처럼 의미를 명시합니다.
- `products`: 1~100개. 각각 고유 `id`, `name`, `sources` (HTTPS `url`, `checked_at` 날짜), `specs`를 갖습니다. 사양은 `{value, unit}`이며 선언 단위와 정확히 같아야 합니다.
- `filters`: `{field, op, value, unit}` 목록을 AND로 적용합니다. `eq`는 타입이 같은 정확한 값 비교, `gte`/`lte`는 숫자 전용입니다. 단위 변환, 문자열 숫자 변환, 동의어 추론은 하지 않습니다.
- `sort`: 선택 사항 `{field, direction: asc|desc}`. 동률은 입력 순서를 유지하고 누락은 양방향 모두 마지막입니다.
- `limit`: 1~100. 필터 통과 수 `matched_count`와 실제 반환 수 `returned_count`를 구분합니다.
- 누락/명시적 null 사양은 `status: unknown`, 제공 사양은 `provided`로 반환합니다. 필터 대상의 누락은 제외 사유 `unknown`으로 기록합니다. 누락된 인증을 false로 바꾸지 않습니다.

시계의 방수 등급과 다이버 인증은 별도 필드로 전달하십시오. 200m 방수로 다이버 인증을 추론하지 않습니다. 케이스 폭과 지름도 각각 별도 필드여야 합니다. 다른 통화·단위는 호출 전에 출처 있는 방식으로 변환하거나 별도 필드로 유지하십시오.

예제 입출력은 manifest.json에 있습니다. 예제의 example.com 제품은 테스트용 가상 자료입니다. 실제 상품 데이터는 저장소에 보관하지 않습니다.

1.1.0부터 기존 비교 입력도 중앙 PostgreSQL의 프로그램 전용 스키마에 자동 저장됩니다. `comparisons` 테이블은 원본 사양·출처·확인일·필터·정렬 조건을 `request_data` JSONB, 반환 결과를 `result_data` JSONB에 보존합니다. `created_at`은 서버 저장 시각이며 출처 확인일과 다릅니다. 결과에는 `compare_id`가 추가됩니다. DB 저장 실패 시 성공 결과를 반환하지 않습니다.

- 저장 내용 조회: `product-comparison {"action":"get","compare_id":"반환된 64자리 ID"}`. 원본 `request`와 `result`를 반환하며 없으면 `found=false`입니다.
- 최근 비교 목록: `product-comparison {"action":"list","limit":20,"offset":0}`. 최신 저장순으로 최대 100개, `has_more`와 다음 페이지용 offset을 지원합니다. offset 상한은 10000입니다.
- 비교 ID는 정렬된 JSON 키로 직렬화한 원본의 SHA-256입니다. 동일 입력의 재호출·동시 호출은 같은 기록을 반환하고 중복 삽입하지 않습니다. 원본 배열 순서·명시적 기본값·사양·확인일이 달라지면 별도 스냅샷입니다. 이전 기록은 덮어쓰지 않습니다. 재조회한 자료의 최신성을 자동 보장하거나 출처를 다시 방문하지 않습니다.

Worker가 중앙 DB에 `tool_<program UUID hex>` 스키마와 제한된 역할을 준비합니다. 프로그램은 주입된 DB 연결로 자기 테이블만 접근하며 외부 인터넷과 메인/다른 프로그램 데이터에 접근하지 못합니다. 테이블과 일반 인덱스는 manifest의 선언으로 관리하고 키 제약이나 임의 SQL migration은 사용하지 않습니다. 별도 DB 컨테이너를 생성하지 않습니다. 구문·단위·동시성·DB 격리·반복 샘플 검증은 폐기 가능한 별도 테스트 스키마에서 실행됩니다. 운영 데이터는 Git에 올리지 않으며 업그레이드 시 기존 스키마와 기록을 유지합니다. 플랫폼 관리자가 접근하는 현재 로컬 단일 사용자 프로그램이며 사용자별 데이터 분리 기능은 없습니다.

1.0.0에서 비교만 하고 저장하지 않은 과거 결과는 자동 복구되지 않습니다. 원본이 남아 있으면 1.1.0으로 다시 호출해 저장해야 합니다.

`generation_tokens.txt`는 코드·테스트 UTF-8 바이트 수를 4로 나누어 올림한 생성 비용 대용값입니다. 실제 세션 청구 토큰이 아니며 manifest의 `generation_tokens_estimated=true`로 구분합니다. 후속 수정 비용은 정책에 따라 누적하고 최종 합계만 저장합니다.

최상위 `storage`는 현재 호출의 DB 처리 결과를 보고합니다: `created` 신규 저장, `updated` 기존 값 변경, `reused` 같은 기록 재사용, `read` 조회. `record_type`과 선택적 `record_id`로 대상을 식별하며 실제 프로그램명은 메인 Registry에서 표시합니다. 트랜잭션 실패 시 성공 결과를 반환하지 않습니다. 이전 저장 결과 안의 상태는 현재 호출 상태가 아닙니다.
